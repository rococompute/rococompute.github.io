tldr

In order to leverage MirageOS unikernels, some changes were needed to solo5 (a secure environment for running unikernels) to work on an ARM-based Macbook. The rest of this page explains what and why unikernels as well as how it ties into the rococompute stack.

unikernels

Instead of inventing a new analogy, I'm going to go and quote a well-written description from Mirage's new website.

When developing an application, we usually rely on a standard interface (commonly known as the POSIX interface) provided by the operating system to interact with hardware devices. In this classic architecture, only the OS kernel has direct access to the physical hardware; it decides how to schedule resources among programs so they can run simultaneously without conflicting with one another.

The main advantage of this setup is portability: since POSIX is widely supported, the same code can theoretically run on Linux, FreeBSD, or macOS. However, each system still has its own quirks and subtle differences. Furthermore, because POSIX is designed for general-purpose computing, it includes a massive amount of software features that a specific application might never actually need.

While this abstraction makes software development easier, it comes at the cost of specialization. Developers are forced to include large blocks of unused code by default which not only wastes resources, but also expands the overall attack surface for security threats.

This is where unikernels emerge as a radical alternative: the application effectively becomes the kernel. There is no longer any separation between the user space and the OS. The application is the only process running within an isolated environment, interacting with virtual devices provided by a hypervisor. A unikernel is therefore a hyper-specialized operating system whose sole purpose is to run your specific application, and nothing else.

When you make an application in a container or virtual machine more secure, you have to sift through dependencies as well as things which are hidden (ie what settings does your ssh service have?). Pinning package versions or whitelisting certain accepted tools all fit under the paradigm of "top-down securitization" whereas unikernels, by requiring every system capabality be explicitly included, fall more under "bottom-up securitization".

verified security

The justification behind having Soma start as a fork of Rocq is that Rocq itself is written in OCaml, meaning plugging in tools such as MirageOS (it itself an OCaml project) can be more a native feature of the stack instead of a separate tool incorporated with "yet another language".

In conjunction with a dependently typed language, the goal is to fully verify the code-generated products (namely applications running in unikernels) instead of augmenting formal verification to existing tools. Standing on top of the shoulders of giants (ie ReasonML), Soma can eventually be a verifiable isomorphic programming framework.
