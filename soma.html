Dynamically typed languages, where you don't need to tell the computer whether a variable is a number or a string, are good for expressiveness and readability. However, being sure of certain properties requires tools like static analysis in your application code or representing abstracted states with formal verification. Eventually, the repo looks less like the codification of business logic and gets a similar smell to a codebase with countless microservices, which defeats the original benefit of an expressivelanguage.

On the other end of the typing spectrum, are dependently typed languages (some examples include Lean, Rocq, Agda, Idris, F*). While historically used for proving theorems in math, there's an important difference to the developer experience in static typed languages like. In languages like Rust or Haskell, once it compiles, the program accomplishes what was written. In dependently typed languages, once it compiles, the program implies a truthiness about the program that was written. In the past, this didn't go mainstream beyond academic applications due to the verbosity required.

To redemy this, let's take a lesson from TypeScript and how JavaScript (even untyped!) works as valid TypeScript:

 // valid TypeScript
const f = x => x * x;

// also valid TypeScript
const g = (x: number): number => x * x;

With dependent types, this looks like (N references natural numbers and Z references integers):

square (x : Any) : N := x * x.

square 12%N.           (* 144%N *)
square (-3)%Z.         (* gives a run-time error *)

Specifying the argument to be a natural number turns square (-3)%Z into instead a compile-time error.

typed_square (x : N) : N := x * x.

typed_square 123.      (* 15129%N *)

Requiring the argument to be even catches more compile-time errors; being able to work with a type that's restrictive of the value itself is a benefit of dependent types. The body is still x * x, but the function now takes a second argument, even, a proof that x is even. Its type, N.even x = true, mentions the first argument's value. The caller supplies the proof: eq_refl is the proof that something equals itself, and the compiler may compute both sides first. N.even 2048 computes to true, so eq_refl proves true = true; for 123 it would have to prove false = true, and the program is rejected.

gradually_typed_square (x : N) (even : N.even x = true) : N := x * x.

gradually_typed_square 2048 eq_refl.   (* 4194304%N *)
gradually_typed_square 123 eq_refl.    (* rejected: 123 isn't even *)

Soma doesn't invent proofs, but a type class can find this one by computing, so the call looks like the ones above. `{Even x} is the proof argument, filled in by trying eq_refl:

Class Even (x : N) := even_proof : N.even x = true.
#[export] Hint Extern 1 (Even _) => exact eq_refl : typeclass_instances.

even_square (x : N) `{Even x} : N := x * x.

even_square 2048.      (* 4194304%N *)
even_square 123.       (* rejected: no instance for "Even 123" *)

Either way the proof is found at compile time, so x has to be known then, as a literal is. For a value that arrives at run time, the program checks N.even x first and passes that check along as the proof.
